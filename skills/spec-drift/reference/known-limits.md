# Known limits

Acknowledged boundaries — do not claim the mechanism has a capability it does not have.

- A `def` written inside an `if`/`try`/`with` produces no symbol; it falls into the `<module>` pseudo-symbol (drift is still detectable at a coarse grain, and using that pseudo-symbol as an anchor is reported by `check` as "does not resolve" with a non-zero exit).
- Blind spots of the "the true source of the assertion is not in the anchors" kind genuinely exist — change the true source and `check` stays silent. The list of the ones already identified is maintained in each project's own ledger, and adding the missing anchor needs `relink --by <owner>`.
- The text matching of `impact` does not catch a call made through an alias after `import ... as alias`, nor `getattr`; a reference missed that way shows up as a blind spot in the reconciliation.
- A move within one file inside a merge commit is not detected.
- Only the one language and the directories `code_root` points at are covered (`code_root` may be configured as several directories, whose union is taken, but it is still one language); contracts outside those directories — the frontend, other languages, configuration — are not covered.
- The spec-drift tool itself lives outside `code_root` (it is a global skill directory), so `check` does not report on it and `changed` does not count it; neither gate verifies the tool's own tests either. Breaking the fingerprint algorithm would be caught loudly, but gutting the judgement logic would be completely silent.
- **`relink` cannot tell "the owner decided what to anchor" apart from "the assistant is adding an anchor it forgot".** `sync`/`relink` are the owner's alone and `confirm` allows the assistant; the intent of that split is "the rule changed, so the owner decides; the code changed and the rule did not, so the assistant can handle it". But adding an anchor straddles both cases: the owner deciding to watch a new symbol is the first, the assistant fixing an anchor it failed to attach when the entry was created is the second, and the tool cannot distinguish them — so the second can only be signed in the owner's name. **The price is that the audit record files the assistant's oversight as the owner's decision.** Met in practice on 2026-09-08 (entry R-ELIG-003 was created with only one of the two functions carrying its rule attached; adding the missing anchor afterwards could only be signed as the owner). The tool is not being changed for now — really splitting them would mean adding a "fixing an omission" sub-form of `relink` that the assistant may use, and that opens the door to "the assistant adds and removes anchors on its own", whose boundary has to be thought through first.
- `changed` needs an external `git` executable: it shells out to git and there is no in-process fallback.
- `changed` requires a configured remote named `origin` (a sub-directory of that name does not count), whose HEAD points at a branch, and a client git ≥ 2.8 with a server that advertises the symref (`ls-remote --symref`; neither older clients nor older servers have been tested).
- The local `origin/HEAD` is never read. After the remote changes its default branch nothing normally has to be done locally; the one exception is a new name that forms a directory/file conflict with an old tracking ref (`main` → `main/next`), which fails loudly and carries git's own `git remote prune origin` hint.
- **Subagents may not see this skill.** In Claude Code a subagent's skill list is a snapshot taken when the parent session started; a plugin installed during the session is invisible to subagents until a new session, and `Skill("spec-drift-mngr:spec-drift")` returns `Unknown skill` there. In one measured session that made the gate fire 0/3 on `sonnet` subagents and 2/2 on `opus` subagents (which found `.spec-drift.json` and read the skill from the plugin cache by hand), while six fresh top-level sessions fired it 6/6 on both models. Workflows that hand the gate to a subagent should paste the skill text or start a new session after installing.
- **The first inventory of an existing file is noisy by construction.** `inventory` enumerates every AST element of the eight kinds without judging it; on a real 1000-line module that came to 569 items, six in ten of them name assignments (⑦) and cross-module calls (④) — the one line `_DIR = os.path.dirname(os.path.dirname(os.path.dirname(os.path.abspath(__file__))))` alone yields five rows (four ④ calls and one ⑦ assignment), and a framework idiom such as `HTTPException(status_code=…, detail=…)` yields two field writes every time it appears. The rows that carry rules (①②③⑧) are diluted by them, and there is no folding or filtering option: the enumeration is exhaustive on purpose, and the verdicts ② and ③ exist precisely to dismiss such rows with a stated reason. Budget for it rather than expecting "fill in two blank columns".
- **A symbol's fingerprint includes the comment block immediately above it.** The fingerprint spans from the first `#` line of the contiguous comment block preceding the `def`/`class`/assignment down to its last line (with one exception: a block that runs unbroken up to line 1 of the file is a file-header comment and is never absorbed), so editing that comment is reported by `check` as fingerprint drift on the symbol and needs a class-B `confirm`. This is deliberate — in code where those comments record the rationale for a constant, they *are* the rule's wording — but a project whose constants carry long, frequently edited comment blocks should expect a dense stream of class-B confirmations, and confirmation fatigue is the failure mode this mechanism itself warns about. Moving such rationale into the ledger entry (where it belongs) and leaving a short comment in the code is the way to keep the stream quiet.
